# Running several server processes with PM2

A single collaboration server process uses one CPU core. To serve more users,
you can run several server processes on the same machine with
[PM2](https://pm2.keymetrics.io/), which shares incoming connections between
them. Live updates (changes, check results and user locations) reach every user
whichever process they are connected to.

These instructions assume you have installed and built Apollo and created a
`.env` file as described in the
[Ubuntu server example](./02-ubuntu-server/index.md).

## Install PM2

```sh
sudo npm install --global pm2
```

## Start the server

The collaboration server includes a PM2 configuration file. From the
`packages/apollo-collaboration-server/` directory, run

```sh
yarn build
pm2 start ecosystem.config.cjs
```

This starts one server process per CPU core. To use a different number of
processes, edit `instances` in `ecosystem.config.cjs`, or change it while the
server is running with

```sh
pm2 scale apollo-collaboration-server 4
```

To restart the processes one at a time without downtime, for example after
updating Apollo, run

```sh
yarn build
pm2 reload apollo-collaboration-server
```

To start the server again when the machine reboots, run `pm2 startup` and follow
its instructions, then run `pm2 save`.

## Things to know

- All processes read the same `.env` file. If you set configuration options
  another way, such as environment variables, make sure every process gets the
  same `MONGODB_URI`, `FILE_UPLOAD_FOLDER`, `JWT_SECRET` and `SESSION_SECRET`.
- Server processes send live updates to each other through a capped collection
  called `serverevents` in the MongoDB database. Its size is set by the
  `EVENTS_COLLECTION_SIZE` option when it is first created.
- Live updates use a long-lived HTTP connection to `/messages/events`. If you
  use a proxy in front of Apollo, don't let it buffer responses or close idle
  connections quickly. The server sends a small message every 30 seconds to keep
  the connection open.
- Apollo creates unique indexes on the names of checks and counters so that
  processes starting at the same time don't create duplicates. MongoDB can't
  create these indexes if duplicates already exist, so when upgrading an
  existing server, check for duplicate checks with

  ```js
  db.checks.aggregate([
    { $group: { _id: '$name', count: { $sum: 1 } } },
    { $match: { count: { $gt: 1 } } },
  ])
  ```

  in `mongosh`, and delete all but one of each.
