# Releasing Apollo

Each release's notes are written once, as a post on the website blog. The GitHub
release and the newsletter email are generated from that post.

## 1. Write the release notes

Create the post, replacing `1.3.0` with the version you're about to release:

```sh
yarn release-notes new 1.3.0
```

This creates `packages/website/blog/<year>/<MM-DD>-v1.3.0/index.md` with:

- a title and a short intro
- `TODO` placeholders for you to fill in
- a "For more information" section listing the pull requests merged since the
  previous release (generated by GitHub)

Fill in the highlights and remove the `TODO` comments. Put screenshots in the
same folder as the post and reference them like `![Description](image.png)`.
Everything above the `<!-- truncate -->` line is the summary shown on the blog
index page.

The post's date comes from its folder name. If the release happens on a later
day, rename the folder to match.

Preview the post with `yarn start` in `packages/website`, and preview the GitHub
release notes with:

```sh
yarn release-notes github 1.3.0
```

## 2. Tag the release

```sh
yarn release -s patch   # or minor, or major
```

This script:

- bumps the package versions
- commits the blog post along with the version changes
- tags the commit and pushes it

It stops before doing anything if the post for the new version is missing or
still contains `TODO` notes. Pass `--skip-notes` to release without a post.

## 3. CI publishes everything

Pushing the tag runs the [Publish workflow](.github/workflows/publish.yml),
which:

1. publishes the packages to npm
2. publishes the Docker images
3. deploys to the production environment
4. creates a draft GitHub release from the blog post

Links to images in the post point to the files on GitHub at the release tag. If
there is no post, the draft uses GitHub's generated notes instead.

## 4. Publish the GitHub release

Open the draft on the [releases page](https://github.com/GMOD/Apollo3/releases),
check it, and publish it. When publishing, make sure "Set as the latest release"
is checked unless this is a fix for an older release line.

If you edit the post after the draft is created, update the GitHub release to
match:

```sh
yarn release-notes github 1.3.0 --create --ref main
```

`--ref main` loads images from `main`, which matters if they weren't in the
tagged commit.

## 5. Send the newsletter (optional)

To turn the post into HTML for a MailerLite email:

```sh
yarn release-notes email 1.3.0 --out release.html
```

Add `--summary` to include only the intro, with a link to the full post. In the
MailerLite campaign editor, add a "Custom HTML" block and paste in the contents
of the file. Images and links use absolute URLs, so they work in the email.
